# jp-freq — частотная справка по японскому

## Задача

Борис учит японский, читает и слушает: подкасты, книги. Встретив незнакомый кандзи
или слово, он хочет за секунды понять **одно**: насколько эта вещь реально
употребляется — и стоит ли вообще тратить на неё силы.

Инструмент отвечает на этот вопрос по корпусу BCCWJ. Больше он не делает ничего.

## Как работать

Борис называет кандзи или слово → запустить `freq.py` и **отдать вывод как есть**.

```
python freq.py 浸              один знак -> справка по кандзи
python freq.py 浸かる           слово     -> справка по слову
python freq.py 扉 唾 引き戸     список    -> сравнительная таблица
python freq.py --html 浸かる    то же самое страницей в out/
python freq.py --check         проверка целостности данных
```

В Cowork по умолчанию идёт `--html`: скрипт печатает только путь, страницу нужно
отдать файлом. Текстовый режим — для быстрой проверки в терминале; его вывод
вставлять в ответ целиком, вывод тула сам к Борису не попадает.

Вердикт скрипт печатает сам, шкалы тоже. Пересказывать вывод своими словами,
переоформлять его в таблицы или дописывать интерпретацию **не надо** — Борис читает
выгрузку напрямую. Комментарий уместен только там, где в данных видно что-то
неочевидное: расхождение SUW и LUW2, перекос по регистрам, ловушка с записью каной.

Развилка определяется автоматически: один иероглиф → трек «кандзи», одно слово →
трек «слово», два аргумента и больше → сравнительная таблица. Переспрашивать не надо.

Таблица — третий тип выдачи, для списка слов (урок, партия карточек): она отвечает
на вопрос «с чего начинать», а не «что это за слово». Полосы вердикта у слов из
одного урока часто совпадают, поэтому в таблице рядом с частотой идут доля записи
знаком и коэффициент SUW/LUW2 — именно они и различают такие слова. Если Борис
просит подробности по одному слову из списка, запускать по нему обычную справку.

Если запрос не нашёлся, скрипт сам предложит леммы, которым принадлежит это
написание, — запустить повторно по предложенной лемме, не спрашивая.

## Скилл

`skill/SKILL.md` — операционная инструкция для чужих чатов: роутинг, «отдавать выдачу
как есть», поведение при ненайденной лемме, запрет отвечать по памяти. Это **не** копия
этого файла: конвенции разработки (знаменатели, как выводятся полосы, как пишутся
подписи) нужны тому, кто правит инструмент, а не тому, кто пробивает слово.

`build_skill.py` пакует `skill/SKILL.md` + `freq.py` + `data/` в `dist/jp-freq-skill.zip`.
Установленная копия — артефакт сборки: правки вносить только в папку проекта, иначе
они теряются при следующей сборке.

Скилл держим один. Развилка по типу запроса уже в коде, а три скилла с почти
одинаковыми описаниями мешали бы друг другу срабатывать.

Данные внутри пакета: `.gz` по умолчанию, `--xz` — запасной вариант на случай лимита
на размер загрузки (23 → 16 МБ ценой более медленной распаковки; `freq.py` читает оба).
Хвост `luw2` не обрезать ради размера: на нём держатся знаменатели.

## Границы

Этот проект **не занимается значениями**. Ни якорей, ни кластеров, ни разбора
морфем, ни сверки с деревом Outlier, ни протоколов — всё это живёт в отдельном
проекте `bccwj-tools` и сюда не переносится. Здесь только частота.

Если Борис спрашивает про значения кандзи — сказать, что это другой инструмент,
и не пытаться выводить значения из частотных данных.

## Данные — только чтение

`data/` выведена из корпуса BCCWJ скриптом `build_data.py`. **Эти файлы не править
никогда**, ни ради опечатки, ни ради «очевидной ошибки в строке».

Причина: расхождение с корпусом ничем себя не выдаёт. Скрипт не упадёт, вердикт
останется правдоподобным, а проверить его будет нечем — числа перестанут значить
то, что они значат. Единственный способ обновления: перезапуск `build_data.py`
на исходном корпусе локально и повторная заливка.

После любой заливки данных прогонять `python freq.py --check`: он сверяет число
строк с зашитыми в `freq.py` константами и ловит тихий дрейф.

Константы `KANJI_TOTAL`, `LUW2_TOTAL`, `SUW_TOTAL`, `KANJI_TOKENS` в `freq.py`
меняются **только** вместе с пересборкой данных и по числам, которые печатает
`build_data.py`. Подогнать константу под данные, чтобы `--check` замолчал, —
худшее, что можно тут сделать.

## Что править можно свободно

`README.md`, этот файл, `docs/*.md` — веду самостоятельно: правлю по факту изменений,
разрешения не спрашиваю, о внесённом уведомляю. Дока обязана соответствовать текущему
состоянию инструмента.

Скрипты `freq.py` и `build_data.py` — по запросу.

## Конвенции изложения

**Ни одного числа без шкалы.** Ранг, частота и доля всегда идут с точкой сравнения.
«Ранг 1414» не значит ничего; «ранг 1414 из 6940, знаки до него закрывают 96,2 %
вхождений» — значит. Скрипт устроен так, чтобы это выполнялось само.

**Подпись под блоком — вывод, а не методичка.** Под каждой таблицей и полосой
стоит одна-две фразы, собранные из чисел **этого** запроса: что они означают
практически. Объяснение метода («шкала логарифмическая», «границы взяты по
покрытию») в справку не идёт — оно живёт в `docs/scale.md`. Проверка простая:
если фразу можно дословно перенести на страницу другого знака, это не вывод.

**В шапке — факты о запросе, не о полосе.** Рядом с ярлыком вердикта стоит частота
самого слова («Встречается раз на 22 500 слов»), ниже — сколько единиц частотнее.
Границы полосы, число слов в ней и её покрытие — свойства шкалы: границы показаны
засечками под полосой в «Месте на шкале частот», остальное живёт в `docs/scale.md`.
Одно и то же число в шапке дважды не повторяется.

**Частоту переводить в «раз на столько-то».** `pmw` в справке не самодостаточен:
чтобы его почувствовать, нужно помнить размер корпуса. Наверх выносится
`10⁶ / pmw` — «раз на 15 тысяч слов», «раз на 102 тысячи символов», — а рядом
даётся таблица известных единиц в тех же единицах. Сам `pmw` остаётся
в подробных таблицах.

**Перед сравнением чисел — проверить знаменатель.** В проекте их четыре
(`docs/data.md`, раздел «Три знаменателя»), и величины с разными знаменателями
рядом не ставятся. Уже случилось дважды: pmw знака сравнивали с массой гнезда,
а покрытие делили на сумму частот `luw2` вместо размера корпуса. Если два числа
не сходятся — сначала подозревать свой знаменатель, а не источник.

**Одно множество — один знаменатель на страницу.** Не смешивать в одной справке
2136 (дзёё) и 2499 (рабочий список). Внешних ориентиров на шкале нет вовсе:
засечками отмечены только границы полос самой справки.

**Сравнивать только сравнимое.** «Первые N знаков корпуса» и «утверждённый список
из N знаков» — разные множества. Если пересечение не посчитано по данным, так
и писать, а не выдавать одно за другое.

**Английские значения из словарей.** Если по ходу называется значение кандзи или
слова, рядом идёт словарный английский эквивалент из JMdict — не перевод с русского.
Нет в словаре — глосс не даётся.

**Предположения помечать явно.** Вывод делается из данных выгрузки. Догадка
допустима, но только с явной пометкой «предположение».

**Грамматические термины по-русски.** Японские пометы разметки (`名詞-普通名詞-一般`,
`動詞-一般`, `形状詞`) поясняются при первом появлении и дальше идут по-русски:
уровень Бориса ~N3, лингвистического образования нет.

## Окружение

Основная площадка — Cowork: файлы загружены **внутрь проекта**, не подключены
локальной папкой. Поэтому работает с телефона и при выключенном компьютере.

Мастер-копия проекта лежит локально в `c:\Users\bkarp\development\jp-freq`
на Windows. Если дока правилась в Cowork — Борис забирает её обратно в мастер-копию.
