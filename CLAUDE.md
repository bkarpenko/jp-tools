# jp-freq — частотная справка по японскому

## Задача

Борис учит японский, читает и слушает: подкасты, книги. Встретив незнакомый кандзи
или слово, он хочет за секунды понять **одно**: насколько эта вещь реально
употребляется — и стоит ли вообще тратить на неё силы.

Инструмент отвечает на этот вопрос по корпусу BCCWJ. Больше он не делает ничего.

## Что ещё лежит в этом репозитории

Репозиторий перестал быть одним инструментом. Сейчас в `tools/` их два:

| каталог | о чём | природа |
|---|---|---|
| `tools/freq/` | частотность по BCCWJ | код + таблицы |
| `tools/outlier-tree-links/` | связки значений дерева Outlier | инструкция для модели |
| `tools/jukugo/` | композициональность компаундов | метод + справочный аппарат |

Всё, что ниже про знаменатели, шкалы, полосы вердикта и данные BCCWJ, относится
**к частотному треку** — то есть к `tools/freq/`. Конвенции изложения (числа со
шкалой, пометки предположений, русские грамматические термины) общие для обоих.
Расслоение этого файла на общее и специфичное — отдельная задача; пока граница
проходит по этому абзацу.

Инструменты друг о друге не знают. Общее у них — только `shared/corpus.py`
(таблицы и знаменатели), и ни `outlier-tree-links`, ни `jukugo` не пользуются даже им.

**Раскладка инструмента без кода** — та же у обоих: `SKILL.md` (читается всегда),
`references/` (подгружается по необходимости), `examples/` (эталоны, на которых
проверяется, что правка не испортила качество). У `jukugo` добавлен четвёртый слой
`docs/` — то, что нужно при правке метода и не нужно при работе; в пакет он не едет.

**Решение, принятое в разговоре, не существует, пока не записано в файл.**
Правило появилось не из общих соображений: при переносе `jukugo` выяснилось, что
пятнадцать позиций метода — включая устройство компаунда как дерева и правило
о неприменимости схемы к 当て字 — были решены в переписке и в файлы не попали.
Часть из них восстановима только из живого чата. Отсюда же требование помечать
провенанс: на чём правило выведено и проверено ли практикой.

## Где живёт проект

Репозиторий https://github.com/bkarpenko/jp-freq (публичный) — единственный источник
правды. Код, дока и таблицы `shared/data/` лежат вместе, поэтому клон
самодостаточен:
доливать ничего не нужно, компьютер Бориса ни для чего не требуется.

### Порядок работы в сессии

1. **Начало.** Склонировать репозиторий в рабочий каталог сессии:
   `git clone https://github.com/bkarpenko/jp-freq.git` (чтение анонимное, ключи
   не нужны). Если правки не планируются, хватит `--depth 1` — быстрее.
2. **Запросы.** Гонять `tools/freq/freq.py` из клона, страницу отдавать файлом.
3. **Правки.** Править файлы в клоне, а не пересказывать правки Борису.
4. **Проверка перед коммитом.** `python tools/freq/freq.py --check`, затем прогнать те типы
   выдачи, которых касалась правка, и посмотреть результат глазами — вёрстку
   проверять скриншотом, а не на глазок по коду.
5. **Коммит и пуш в той же сессии.** Контейнер эфемерный: всё, что не отправлено,
   исчезает вместе с ним.

Сообщения коммитов — по-русски, в том же стиле, что и дока: что изменилось и почему,
а не «update files».

### Право на запись

Чтение публичного репозитория анонимно, **запись — нет**, и одного токена мало:
git-трафик облачной сессии идёт через прокси, который подставляет ключ только для
репозиториев из списка источников сессии. Чужой токен он не пропускает — пуш падает
с «not in this session's authorized repository set».

Отсюда правило: репозиторий должен быть добавлен источником в саму сессию. Если он
не добавлен — пуш невозможен, и об этом надо сказать сразу, а не копить правки
в никуда. Запасной путь, пока сессия привязана к компьютеру: коммит и пуш из клона
в подключённой папке.

Токен, если он всё же используется, нигде не сохранять: ни в памяти, ни в доке,
ни в коммитах.

### Локальная копия на компьютере

Папка `jp-freq` на машине Бориса — теперь просто ещё один клон, и он может отстать.
Если сессия привязана к компьютеру, перед правками делать `git pull` в этой папке;
если нет — не трогать её вовсе и работать в облачном клоне.

## Как работать

Борис называет кандзи или слово → запустить `freq.py` и **отдать вывод как есть**.

```
python tools/freq/freq.py 浸              один знак -> справка по кандзи
python tools/freq/freq.py 浸かる           слово     -> справка по слову
python tools/freq/freq.py 扉 唾 引き戸     список    -> сравнительная таблица
python tools/freq/freq.py --html 浸かる    то же самое страницей в out/
python tools/freq/freq.py --check         проверка целостности данных
```

В Cowork по умолчанию идёт `--html`: скрипт печатает только путь, страницу нужно
отдать файлом. Текстовый режим — для быстрой проверки в терминале; его вывод
вставлять в ответ целиком, вывод тула сам к Борису не попадает.

Вердикт скрипт печатает сам, шкалы тоже. Пересказывать вывод своими словами,
переоформлять его в таблицы или дописывать интерпретацию **не надо** — Борис читает
выгрузку напрямую. Комментарий уместен только там, где в данных видно что-то
неочевидное: расхождение SUW и LUW2, перекос по регистрам, ловушка с записью каной.

Развилка определяется автоматически: один иероглиф → трек «кандзи», одно слово →
трек «слово», два аргумента и больше → сравнительная таблица. Переспрашивать не надо.

Таблица — третий тип выдачи, для списка слов (урок, партия карточек): она отвечает
на вопрос «с чего начинать», а не «что это за слово». Полосы вердикта у слов из
одного урока часто совпадают, поэтому в таблице рядом с частотой идут доля записи
знаком и коэффициент SUW/LUW2 — именно они и различают такие слова. Если Борис
просит подробности по одному слову из списка, запускать по нему обычную справку.

Если запрос не нашёлся, скрипт сам предложит леммы, которым принадлежит это
написание, — запустить повторно по предложенной лемме, не спрашивая.

## Скилл

`tools/freq/SKILL.md` — операционная инструкция для чужих чатов: роутинг, «отдавать выдачу
как есть», поведение при ненайденной лемме, запрет отвечать по памяти. Это **не** копия
этого файла: конвенции разработки (знаменатели, как выводятся полосы, как пишутся
подписи) нужны тому, кто правит инструмент, а не тому, кто пробивает слово.

`build_skill.py` пакует то, что перечислено в `tools/freq/skill.json` — `SKILL.md`,
`freq.py`, `shared/corpus.py` и таблицы — в `dist/jp-freq-skill.zip`.
Установленная копия — артефакт сборки: правки вносить только в репозиторий, иначе они
теряются при следующей сборке. Собирать — из свежего клона (или после `git pull`),
чтобы в пакет не уехало полуготовое состояние рабочей копии.

Скилл несёт данные внутри и в сеть не ходит: тянуть их из репозитория на каждый
запрос было бы медленнее чтения соседнего файла и потребовало бы сети там, где её
может не быть. Репозиторий — источник сборки, а не источник времени выполнения.

**Скилл на инструмент, а не на тип запроса.** У частотки развилка кандзи / слово /
таблица живёт в `freq.py`: три скилла с почти одинаковыми описаниями конкурировали бы
за срабатывание. А `jp-freq` и `outlier-tree-links` не конфликтуют — одному нужна
частота, другому дерево значений, — и держать их порознь правильно.

**Скилл — побочный продукт, а не главный путь.** Основной способ работы — Claude
читает репозиторий напрямую. Пакет нужен там, где репозитория нет: телефон, чужой
чат, выключенная машина. Отсюда и приоритеты: если правка улучшает работу с
репозиторием, но усложняет упаковку, выбирается репозиторий.

Данные внутри пакета: `.gz` по умолчанию, `--xz` — запасной вариант на случай лимита
на размер загрузки (23 → 16 МБ ценой более медленной распаковки; `freq.py` читает оба).
Хвост `luw2` не обрезать ради размера: на нём держатся знаменатели.

## Границы

Этот проект **не занимается значениями**. Ни якорей, ни кластеров, ни разбора
морфем, ни сверки с деревом Outlier, ни протоколов — всё это живёт в отдельном
проекте `bccwj-tools` и сюда не переносится. Здесь только частота.

Если Борис спрашивает про значения кандзи — сказать, что это другой инструмент,
и не пытаться выводить значения из частотных данных.

## Данные — только чтение

`shared/data/` выведена из корпуса BCCWJ скриптом `shared/build_data.py`. **Эти файлы не править
никогда**, ни ради опечатки, ни ради «очевидной ошибки в строке».

Причина: расхождение с корпусом ничем себя не выдаёт. Скрипт не упадёт, вердикт
останется правдоподобным, а проверить его будет нечем — числа перестанут значить
то, что они значат. Единственный способ обновления: перезапуск `build_data.py`
на исходном корпусе локально и повторная заливка.

После любой заливки данных прогонять `python shared/corpus.py`: он сверяет число
строк с зашитыми константами и ловит тихий дрейф. То же делает
`python tools/freq/freq.py --check` — это тот же вызов из инструмента.

Константы `KANJI_TOTAL`, `LUW2_TOTAL`, `SUW_TOTAL`, `KANJI_TOKENS` в `shared/corpus.py`
меняются **только** вместе с пересборкой данных и по числам, которые печатает
`build_data.py`. Подогнать константу под данные, чтобы `--check` замолчал, —
худшее, что можно тут сделать.

## Что править можно свободно

`README.md`, этот файл, `docs/*.md` — веду самостоятельно: правлю по факту изменений,
разрешения не спрашиваю, о внесённом уведомляю. Дока обязана соответствовать текущему
состоянию инструмента.

Скрипты `tools/freq/freq.py`, `shared/corpus.py`, `shared/build_data.py`
и `build_skill.py` — по запросу.

## Конвенции изложения

**Ни одного числа без шкалы.** Ранг, частота и доля всегда идут с точкой сравнения.
«Ранг 1414» не значит ничего; «ранг 1414 из 6940, знаки до него закрывают 96,2 %
вхождений» — значит. Скрипт устроен так, чтобы это выполнялось само.

**Подпись под блоком — вывод, а не методичка.** Под каждой таблицей и полосой
стоит одна-две фразы, собранные из чисел **этого** запроса: что они означают
практически. Объяснение метода («шкала логарифмическая», «границы взяты по
покрытию») в справку не идёт — оно живёт в `tools/freq/docs/scale.md`. Проверка простая:
если фразу можно дословно перенести на страницу другого знака, это не вывод.

**В шапке — факты о запросе, не о полосе.** Рядом с ярлыком вердикта стоит
адрес слова в списке: «Ранг 1 604 · 42,95 pmw». Границы полосы, число слов в ней
и её покрытие — свойства шкалы: границы показаны засечками под полосой в «Месте
на шкале частот», остальное живёт в `tools/freq/docs/scale.md`.

**Частоту переводить в «раз на столько-то».** `pmw` не самодостаточен: чтобы его
почувствовать, нужно помнить размер корпуса. Поэтому рядом с ним везде, где есть
место, стоит `10⁶ / pmw` — «раз на 15 тысяч слов», «раз на 102 тысячи символов»:
в плитке метрик, в таблице шкалы, на её концах. В шапке слова с 01.09.2026 стоит
пара «ранг · pmw» — Борис просил именно её; это сознательное исключение, и оно
стоит того, что ранг и частота там повторяют плитки метрик под шапкой.

**Ранг в luw2 делится.** Одинаковая частота — одинаковый ранг: на 108 380-м стоят
4 382 слова. Соседи в таблице шкалы берутся по факту, строкой выше и строкой ниже,
поэтому три строки подряд с одним числом — не ошибка. Однорангники помечены «=»,
под таблицей сказано, сколько слов делит ранг.

**Баланс должен сходиться, и сходиться внутри одной таблицы.** «Сам» и «в составе»
в блоке «слово или морфема» считаются как `freq_s` и `freq_s - freq_l` — обе величины
из suw, поэтому сумма даёт ровно 100 % при любом слове. Вторая доля берётся
вычитанием из ста, а не делением: два округления порознь дают 28,6 + 71,5 = 100,1.
Список составных из luw2 этот баланс **иллюстрирует, а не образует**: его покрытие
названо отдельной строкой, а если он баланс перебирает (поиск идёт по написанию,
разметка — по морфеме), на карточке стоит предупреждение.

**Перед сравнением чисел — проверить знаменатель.** В проекте их четыре
(`shared/docs/data.md`, раздел «Три знаменателя»), и величины с разными знаменателями
рядом не ставятся. Уже случилось дважды: pmw знака сравнивали с массой гнезда,
а покрытие делили на сумму частот `luw2` вместо размера корпуса. Если два числа
не сходятся — сначала подозревать свой знаменатель, а не источник.

**Одно множество — один знаменатель на страницу.** Не смешивать в одной справке
2136 (дзёё) и 2499 (рабочий список). Внешних ориентиров на шкале нет вовсе:
засечками отмечены только границы полос самой справки.

**Сравнивать только сравнимое.** «Первые N знаков корпуса» и «утверждённый список
из N знаков» — разные множества. Если пересечение не посчитано по данным, так
и писать, а не выдавать одно за другое.

**Английские значения из словарей.** Если по ходу называется значение кандзи или
слова, рядом идёт словарный английский эквивалент из JMdict — не перевод с русского.
Нет в словаре — глосс не даётся.

**Предположения помечать явно.** Вывод делается из данных выгрузки. Догадка
допустима, но только с явной пометкой «предположение».

**Грамматические термины по-русски.** Японские пометы разметки (`名詞-普通名詞-一般`,
`動詞-一般`, `形状詞`) поясняются при первом появлении и дальше идут по-русски:
уровень Бориса ~N3, лингвистического образования нет.

## Окружение

Мастер-копия — репозиторий на GitHub (см. «Где живёт проект»). Работа идёт в клоне
внутри сессии, компьютер Бориса не нужен: справка работает с телефона и при
выключенной машине. Прежняя схема — мастер-копия в `c:\Users\bkarp\development\jp-freq`
и ручной перенос правок обратно — отменена; та папка теперь обычный клон.

Скилл `jp-freq` (см. «Скилл») — третья площадка: он несёт данные с собой и работает
в любом чате, даже без сети. Пересобирается из репозитория, правится только там.
