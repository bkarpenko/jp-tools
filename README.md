# Инструменты для японского

Три инструмента вокруг одной задачи: Борис учит японский — читает, слушает, — и по
ходу возникают вопросы, на которые словарь не отвечает. Каждый инструмент отвечает
ровно на один такой вопрос и не лезет в чужой.

| инструмент | на какой вопрос отвечает | природа |
|---|---|---|
| [`tools/freq`](tools/freq/README.md) | насколько слово или знак реально употребляется | код + таблицы BCCWJ |
| [`tools/jukugo`](tools/jukugo/README.md) | складывается ли значение компаунда из значений его знаков | метод + справочный аппарат |
| [`tools/outlier-tree-links`](tools/outlier-tree-links/SKILL.md) | почему одно значение знака породило другое | инструкция для модели |

Инструменты друг о друге не знают. Общее у них — таблицы корпуса и знаменатели
в `shared/corpus.py`, и пользуется ими пока только `freq`.

Репозиторий самодостаточен: код, дока и таблицы лежат вместе, клона достаточно
для работы, доливать ничего не нужно.

```
git clone https://github.com/bkarpenko/jp-tools
cd jp-tools
```

## Быстрый старт

**Частотность** — единственный инструмент с кодом:

```
python tools/freq/freq.py 浸              один знак -> справка по кандзи
python tools/freq/freq.py 浸かる           слово     -> справка по слову
python tools/freq/freq.py 扉 唾 引き戸     список    -> сравнительная таблица
python tools/freq/freq.py --html 浸かる    то же самое страницей
python tools/freq/freq.py --check         проверка целостности данных
```

Подробности — [tools/freq/README.md](tools/freq/README.md).

**Композициональность компаундов и связки значений дерева** кода не имеют: это методы,
по которым работает модель. Читаются как документы — [`tools/jukugo/SKILL.md`](tools/jukugo/SKILL.md)
и [`tools/outlier-tree-links/SKILL.md`](tools/outlier-tree-links/SKILL.md), — и оба
требуют входных материалов: словарных статей, карточки Outlier.

## Раскладка

```
build_skill.py           сборка скиллов в dist/ по манифестам tools/*/skill.json
shared/                  общее для всех инструментов
  corpus.py              где лежат таблицы, как читаются, чем нормируются
  data/                  таблицы, выведенные из корпуса: только чтение
  build_data.py          пересборка data/ из сырого BCCWJ — в обычной работе не нужен
  docs/data.md           что в таблицах и откуда взято
tools/freq/              частотность: код + таблицы
tools/jukugo/            композициональность компаундов: метод + справочный аппарат
tools/outlier-tree-links/  связки значений дерева Outlier: инструкция для модели
docs/workflow.md         схема работы: сессия, запись в репозиторий, обновление скилла
```

Внутри каталога инструмента — всегда `SKILL.md` (читается всегда), `skill.json`
(манифест сборки) и то, что инструменту нужно: код, `references/` для подгружаемого
по необходимости, `examples/` для эталонов, `docs/` для того, что нужно при правке
метода и не нужно при работе.

**Новый инструмент добавляется каталогом в `tools/`** — `SKILL.md`, `skill.json`
и содержимое. `build_skill.py` править при этом не нужно: он не знает ни одного
инструмента по имени, а обходит манифесты.

## Скиллы: то же самое в любом чате Claude

`build_skill.py` собирает каждый инструмент в скилл по его манифесту. Скилл несёт
всё нужное с собой и потому работает там, где репозитория нет: телефон, чужой чат,
выключенная машина. Основной путь — Claude читает репозиторий напрямую; пакет нужен
для остальных случаев.

```
python build_skill.py          все скиллы в dist/
python build_skill.py freq     только один инструмент
python build_skill.py --xz     данные в .xz: jp-freq 23 -> 17 МБ, распаковка медленнее
```

Размеры пакетов: `jp-freq` 23 МБ (несёт таблицы), `jukugo` 0,5 МБ,
`outlier-tree-links` 24 КБ. Zip загружается в настройках Claude руками.

**Источник правды — репозиторий.** Установленная копия скилла правке не подлежит:
правится файл в репозитории, потом пересборка и перезаливка. Иначе через месяц
не отличить, какая версия настоящая. Собирать — из свежего клона, чтобы в пакет
не уехало полуготовое состояние рабочей копии.

**Скилл собирается на инструмент, а не на тип запроса.** У частотки развилка
кандзи / слово / таблица живёт внутри `freq.py`: три скилла с почти одинаковыми
описаниями конкурировали бы за срабатывание. Границы между тремя существующими
держатся описаниями во фронтматтере, и при правке любого из них границу надо
проверять заново — подробности в `CLAUDE.md`.

## Данные не редактируются

`shared/data/` выведена из корпуса BCCWJ скриптом `shared/build_data.py`. Правка
в сессии тихо разведёт числа с корпусом: вердикт останется правдоподобным, а проверить
его будет нечем. Обновление — только пересборкой из исходного корпуса, после неё
обязателен `python shared/corpus.py`.

То же правило действует на справочный аппарат `jukugo`: `references/SCHEMA.md`
воспроизводит внешний источник, и расхождение с ним ничем себя не выдаёт.
